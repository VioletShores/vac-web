Memory & Context Stream (P-SC) · Plan · S142 · 21 July 2026

How AthenaPilot Remembers People

Today, AthenaPilot forgets who you are between conversations. Tell it your name or "reply in Italian" and tomorrow it starts blank. This is the third of three blockers stopping real users from being invited onto the product. This plan defines what gets remembered, how it's stored, how it travels, how it's deleted — and the smallest cut that ships in one week.

What the cross-model gate changed (read this first)

The original plan (from the constellation-digest feature F-701 and the three-tier memory feature F-150) was: build the full packet metadata envelope first, then the memory tiers, then a ~1KB portable digest carried in every packet. That plan was put through a multi-model challenge gate — run through AthenaPilot's own orchestration engine (/v1/orchestrate, challenge mode), which is itself proof the product works — and the gate rejected the sequencing and found seven failure classes the plan missed. The verdicts below are adopted as binding (the L-2312 rule: when independent models converge on a weakness, it's a fix, not an opinion).

Gate verdicts adopted

  • Don't build the full envelope first. Only a thin envelope (identity, message id, conversation id, consent flag, memory version) is on the critical path. Cost, trust scores, stage timestamps come later.
  • "Immutable" hot facts are wrong. Names and preferences change. Every fact needs status (active / superseded / deleted), a source message id, confidence, and a timestamp. Deletion works by tombstone, not erasure of history.
  • A post-conversation digest job fails on WhatsApp — conversations don't cleanly end. Explicit facts ("call me Rob", "reply in Italian") must be written immediately, on the message that states them.
  • Conflict order must be explicit: current user instruction beats stored fact beats summary beats old history. Without this, memory becomes sticky and wrong.
  • 1KB is a profile card, not a memory. Hot facts with source-ids fit in 1KB; episodic history with provenance does not. The digest is a cache; the central store is the source of truth — otherwise "forget me" can never be honoured (digests copied into logs, queues, traces).
  • v1 write policy, hard rules: first-party facts only, stated explicitly by the sender, in 1:1 chats. No third-party facts, no group chats, no assistant inferences, no summary-derived "facts".
  • User controls ship on day one: "what do you remember about me?", "forget my language preference", "forget me".

The one-week cut SHIP FIRST

Steps 1–3 only. Four memory keys to start: preferred_name, preferred_language, communication_style, hard_constraints. Explicit statements only. No summarisation, no warm tier, no digest.

Acceptance tests (all five must pass, live on WhatsApp)

  1. Core: "Call me Rob, reply in Italian" today → a brand-new conversation tomorrow greets Rob in Italian.
  2. Correction: "actually, English from now on" → new conversation uses English.
  3. Deletion: "forget my language preference" → new conversation makes no language assumption.
  4. No contamination: "my brother speaks French" → French is not stored as the user's language.
  5. No inference: an assistant guess ("sounds like you're vegetarian?") never becomes a stored fact.

Plus explainability: asked "why Italian?", the bot answers "you told me yesterday" and internal debug shows the source message id.

Research questions for the IDSIA collaboration

Candidate topics for the Andrea Danani / SUPSI-IDSIA work packages — where AthenaPilot's memory becomes a live research testbed rather than just product plumbing.

  • Trust-calibrated memory. Extraction confidence is a calibration problem: can the same trust-scoring machinery that ranks models (SignalRank) score memory writes — and can miscalibration be measured against user-correction events as ground truth?
  • Forgetting as a control problem. TTLs, supersession, and confidence decay form a control loop. What decay policy minimises both staleness errors and unnecessary re-asking?
  • Provenance-auditable memory vs. retrieval. Every stored fact here carries a source message id — memory as an audit chain. How does answer quality and user trust compare against retrieval-only (RAG) baselines with no provenance?
  • Contamination detection benchmarks. The gate enumerated contamination classes (assistant-inference, summary-to-fact, third-party, injection, language bleed). These are a labelable benchmark: can a payload-aware classifier catch them at write time, and what's the precision floor before real users?
  • Privacy-preserving portable digests. When the digest travels cross-surface, what's the minimum disclosure design (source-ids not provenance, hot-only, expiring versions) that preserves utility — and can deletion propagation be formally verified?

Why this ladders to revenue

Memory is blocker three of three for inviting real users (after the message template, done, and the language fix, pending your Italian test). The first invitees — Anthony's Regatta Club staff, Sam at Blue Water Digital — experience the product as trustworthy precisely when it remembers them correctly and can prove why. Nothing here is research for its own sake: steps 1–3 are the minimum that turns AthenaPilot from a demo into something a stranger can use twice.
