## 2. Continuous Coding Corpus Design

### 2.1 Design Principles

Mirror the `athena_challenge` pattern (test_harness.py `SEED_CORPUS`) exactly:
- Every question has `question`, `known_answer`, `scoring_criteria`, `domain`, `knowledge_type`, `difficulty`, `source`
- Coding domain uses `knowledge_type: PROCEDURAL` with execution-verified scoring where possible
- Questions are **self-contained** (no external repo state required) for synchronous evaluation
- Questions with **executable ground truth** are flagged `"executable": True` — harness runs the model's code and checks output, no LLM judge needed

### 2.2 Five Task Classes + Question Schema

#### Class 1: Bugfix
```python
{
    "domain": "coding_bugfix",
    "knowledge_type": "PROCEDURAL",
    "executable": True,
    "question": "The following Python function has a bug. Fix it so all test cases pass.\n\n<code>...</code>\n\nTest cases: [...]",
    "known_answer": "<corrected_code>",
    "test_cases": [{"input": ..., "expected": ...}, ...],   # harness executes
    "scoring_criteria": "Code must pass all N test cases when executed. Partial credit: K/N passing tests.",
    "difficulty": "easy|medium|hard",
    "source": "internal|leetcode|exercism|real-codebase",
}
```
**Scoring:** Execute model output → run test cases → score = passing_tests / total_tests. No LLM judge needed. Maps to `KnowledgeType.PROCEDURAL` with execution path.

#### Class 2: Greenfield (Code Generation)
```python
{
    "domain": "coding_greenfield",
    "knowledge_type": "PROCEDURAL",
    "executable": True,
    "question": "Write a function that... [spec with examples]",
    "known_answer": "<reference_implementation>",
    "test_cases": [...],    # harness executes model output
    "scoring_criteria": "...",
}
```

#### Class 3: Refactor
```python
{
    "domain": "coding_refactor",
    "knowledge_type": "CAUSAL",
    "executable": False,   # output is structurally judged
    "question": "Refactor this function to [goal]. Preserve behavior.",
    "known_answer": "<refactored_version_with_rationale>",
    "scoring_criteria": "Must: (1) preserve external API, (2) achieve stated goal, (3) no regressions. LLM judge + optional execution.",
    "check_equivalence": True,   # harness calls both old + new on sample inputs, diffs outputs
}
```

#### Class 4: Test Writing
```python
{
    "domain": "coding_tests",
    "knowledge_type": "PROCEDURAL",
    "executable": True,
    "question": "Write pytest tests for this function. It must catch: [bug list]",
    "known_answer": "<test_suite>",
    "ground_truth_bugs": [<buggy_versions>],   # harness runs model's tests against buggy code; tests pass iff bugs caught
    "scoring_criteria": "Score = bugs_caught / total_bugs. Bonus: minimal false positives on clean code.",
}
```
**Scoring is inverted:** good tests catch bugs (fail on buggy code, pass on clean code).

#### Class 5: Terminal Ops
```python
{
    "domain": "coding_terminal",
    "knowledge_type": "PROCEDURAL",
    "executable": True,    # harness runs command in sandbox
    "question": "Write a bash/python one-liner to [task]. Input: [description]. Output: [expected format].",
    "known_answer": "<command>",
    "sandbox": "bash",    # executor: subprocess in restricted tmpdir
    "test_inputs": [...],
    "expected_outputs": [...],
    "scoring_criteria": "Execute command on each test input, compare output exactly or regex.",
}
```

### 2.3 Corpus Scale (first calibration batch)

| Domain | Q Count (initial) | Difficulty Mix | Executable? |
|---|---|---|---|
| coding_bugfix | 25 | 10 easy / 10 med / 5 hard | 100% |
| coding_greenfield | 25 | 8 easy / 12 med / 5 hard | 100% |
| coding_refactor | 15 | 5 easy / 7 med / 3 hard | 50% (equivalence check) |
| coding_tests | 15 | 5 easy / 7 med / 3 hard | 100% (inverted) |
| coding_terminal | 20 | 10 easy / 8 med / 2 hard | 100% |
| **TOTAL** | **100** | | **~90% executable** |

90%+ executable = 90%+ of coding scores require zero LLM judge. This is the key upgrade over the current `code` domain (which uses pure LLM judging).

### 2.4 Harness Changes Required

The existing `test_harness.py` runs `PROCEDURAL` scoring via LLM judge only. Two additions:

1. **`execute_code(code: str, test_cases: list, sandbox: str) -> ScoringResult`** — subprocess with restricted env, 10s timeout per test, returns pass/fail per case.
2. **`DOMAIN_TYPE_DEFAULTS` extension** — add `coding_bugfix`, `coding_greenfield`, `coding_refactor`, `coding_tests`, `coding_terminal` with `PROCEDURAL` type + `executable=True` flag.

Existing cross-model judging still runs as fallback for non-executable items (coding_refactor partial).

### 2.5 Trust Score Destination

Each of the 5 coding sub-domains gets an independent per-model trust score in the trust graph, exactly like the existing domains (`medical`, `financial`, etc.). The router can then select the best model for "coding_bugfix" separately from "coding_terminal" — this is the sub-domain granularity gap called out in the North Star doc (limitation #3).

### 4.3 Zero-Marginal Lane Value

Local models are valuable not for quality parity but for:
1. **Zero API cost** — run 1000 calibration questions without budget approval
2. **Speed without quota** — no rate limits, no 429s
3. **Data privacy** — no external API call for sensitive internal corpus questions
4. **Baseline anchor** — establishes a free quality floor; routing to API only when local can't solve

**Recommended local setup:** Ollama (already common on Mac Mini) + `qwen2.5-coder:32b-instruct-q4_K_M`. MLX-LM if you want Apple Silicon native speed (+20–30% over llama.cpp for Metal-accelerated shapes).
